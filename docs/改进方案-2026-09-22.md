## 2. 预警与通知

### 2.0 现状链路

一次判定要经过这几步，全部落在两个文件里：

```swift
// MenuBarController.swift:424-425  每轮 refresh 成功后
self.checkAlerts()
```

```swift
// MenuBarController.swift:523-545
func checkAlerts() {
    let values = AlertEngine.extractValues(gold: gold, sectors: allSectors, funds: funds)
    let (triggerIdx, resetIdx) = AlertEngine.checkAll(rules: alertConfig.rules, values: values)
    for i in triggerIdx {
        let rule = alertConfig.rules[i]
        if let value = values[AlertEngine.ruleKey(rule)] {
            notifier.sendNotification(rule: rule, currentValue: value)
        }
        alertConfig.updateStatus(at: i, triggered: true)
    }
    for i in resetIdx { alertConfig.updateStatus(at: i, triggered: false) }
}
```

三个特征：

1. **输入是即时值**：`extractValues` 取黄金现价 `priceCNY`、板块盘中涨跌幅 `changePct`、基金官方净值 `nav`（`Alert/AlertEngine.swift:94-109`）。
2. **闸门是位置**：`shouldTrigger` 判 `value >= / <= threshold`，且 `!rule.triggered`（`Alert/AlertEngine.swift:11-19`）。
3. **输出是一次通知 + 一个布尔**：状态只有 `triggered` / `triggeredAt`（`Alert/AlertRule.swift:32-33`）。

下面 10 条都改这三件事。

### W1 判定口径：改成「日终判定价」

**现状**：拿即时价跟阈值比大小，比较结果就是结论。

```swift
// Alert/AlertEngine.swift:11-19
static func shouldTrigger(rule: AlertRule, value: Double) -> Bool {
    guard rule.enabled, !rule.triggered else { return false }
    switch rule.direction {
    case .above: return value >= rule.threshold
    case .below: return value <= rule.threshold
    }
}
```

按标的拆开看，输入分别是什么（`Alert/AlertEngine.swift:94-109`）：

| 标的 | 判定价来源 | 性质 |
|---|---|---|
| 黄金 | `gold.priceCNY` | 沪金主连现价，含夜盘，每 30s 变一次 |
| 板块 | `sector.changePct` | 盘中实时涨跌幅 |
| 基金净值 / 涨跌幅 | `fund.quote.nav` / `navChangePct` | 官方净值，一天一变 |

三个后果：

1. **盘中插针即触发。** 黄金现价和板块涨跌幅都是盘中值，你的《投资总纲》写的是「盘中插针 = 噪音，连续 2 天收盘跌破才算真触发」，这里是它的反面。
2. **触发后横盘不再出声。** 黄金涨到 700 响一次，此后只要不跌回 696.5（`AlertEngine.swift:52-57` 的 0.5% 相对迟滞）就一直静音。价格在 700 上方站十天，你只收到一条通知。
3. **「连续几天」这个维度不存在。** 规则里没有确认天数，也没有「今天是第几天」的地方可放。

**对照**：my-app 第 85 批把这一层重写了，理由写在 `api/market-poller.js:35-48`，三条与上面三个后果一一对应。它的判定口径一句话（`:50-52`）：

> 在触发区内 + 出现有意义的**新判定价** → 再推一条。「有意义」的粒度由**判定价自己的日期**决定 —— 一天只有一个判定价（日终），所以「跨日」天然等于「有了新的权威数字」。

「判定价」是关键词：**当日唯一的权威值，且自带日期**。基金取净值 PDATE，行情取 f124，上海金取行情源的日期字段（`api/market-poller.js:31-32`）。

顺带解决一件事：**「连续 N 个交易日」不需要交易日历**。非交易日没有新 pdate，评估自然不进入；周五到周一的推进天然算相邻两天（`api/db.js:159-164`）。这是上一版把交易日历列为预警前置项的错误，R1 里已降到界面状态。

**改法**：三步，第一步是本条与 W4 的共同前置。

**第一步（前置）：拿到行情源自己给的日期。**

现在的 `GoldQuote.date` 不是行情日期，是本地时钟格式化的：

```swift
// Data/DataLayer.swift:98-111
let now = Date()
let fmtDate = DateFormatter(); fmtDate.dateFormat = "yyyy-MM-dd"
let fmtTime = DateFormatter(); fmtTime.dateFormat = "HH:mm:ss"
return GoldQuote(
    priceCNY: (first["f2"] as? Double) ?? 0,
    ...
    time: fmtTime.string(from: now),   // ← 抓取时刻
    date: fmtDate.string(from: now)    // ← 抓取日期
)
```

请求的字段里也没有 f124（`Data/DataLayer.swift:91` 请求的是 `f2,f3,f4,f5,f6,f12,f14,f15,f16,f17,f18`）。三处要改：

| 标的 | 改法 | 证据 |
|---|---|---|
| 黄金 | 请求加 `f124`，`time`/`date` 改为由 f124 推导 | `DataLayer.swift:91` |
| 板块 | `SectorQuote` 加 `quoteDate: String`，请求加 `f124` | `DataLayer.swift:118-125`、`:189-193` |
| 基金 | 已现成 —— `navDate` 就是 PDATE | `DataLayer.swift:366` |

`f124` 是 unix 秒。转日期要先平移到 +08:00 再取 UTC 分量，直接用 `toISOString()` 在晚 20:00 之后会整体差一天（`api/market-poller.js:129-138` 记录了这一点，夜盘尤其明显）。

**第二步：判定输入换成判定价，判定时点交给 W4。**

`extractValues` 不再返回裸值，改成返回 `(value, pdate)` 对：

```swift
struct JudgedValue { let value: Double; let pdate: String }   // pdate = 判定价自带日期
```

`pdate` 拿不到或晚于今天 → 本轮不评估这条线（`api/market-poller.js:426-431`）。

**第三步：闸门从「位置」改成「有新判定价」。**

去掉 `!rule.triggered` 这个位置闸门。推送条件变成：在触发区内 + 这条线的 pdate 与上次推送的不同（`api/market-poller.js:60`、`:466-471`）。同时注意一条 my-app 踩过的坑 —— 「更糟才推」的判据必须带**轮次边界**（上次推送还属不属于本轮穿越）：价格复位后回到同一个数字（真金白银里极常见）会被误当成「没变化」静默吞掉，比重复提醒更糟（`:462-465`）。

**验收判据**：
- 造一段「周二收盘 701、周三收盘 702、周四收盘 703」的序列，在收盘价口径下应推 3 条，事件表 3 行，pdate 各不相同。
- 造一段盘中插针（现价瞬间 705 又收回 698），当日收盘 698，不应推送。
- 黄金在 22:00（夜盘）拿到 705，当日日盘收盘是 698，不应推送 —— 这条专测 W4 的时点闸门。

### W2 确认天数

**现状**：规则里没有这个字段。

```swift
// Alert/AlertRule.swift:23-35
struct AlertRule: Codable, Identifiable, Hashable {
    var id: String
    var targetType: AlertTargetType
    var targetCode: String
    var targetName: String
    var direction: AlertDirection
    var threshold: Double
    var label: String
    var enabled: Bool
    var triggered: Bool
    var triggeredAt: Date?
    var fundMetric: FundMetric?
}
```

**对照**：my-app 的状态机（`api/market-poller.js:54-58`）：

```
idle ──首个 OUTSIDE──▶ counting ──days ≥ confirmDays──▶ confirmed
  ▲                        │                              │
  └────── INSIDE（跌破复位价）───────────────────────────┘
HOLD（阈值与复位价之间的迟滞区）→ 冻结：不 +1 也不清零
```

三态位置判定是 `position()`（`api/market-poller.js:301-327`），推进是纯函数 `advance()`（`:329-346`）。确认天数 1–10（`:335`），默认 1。

HOLD 分支是最容易做错的地方：价格在阈值附近抖动时若并进 INSIDE，计数被反复清零，永远到不了确认天数 —— 那等于确认天数这个功能不存在（`:306-307`）。

**改法**：
1. `AlertRule` 加 `confirmDays: Int?`（缺省 1，保持现有行为）与 `resetThreshold: Double?`（缺省走现有 0.5% 迟滞，`AlertEngine.swift:25-59` 的差异化迟滞保留为兜底）。
2. 新增 `Alert/AlertStateMachine.swift`，把 `position()` / `advance()` 按 my-app 的语义移植成两个纯函数。
3. `shouldTrigger` 换成 `advance(prev:pos:confirmDays:pdate:)`，只有返回 `confirmed` 才进通知。
4. 设置页的添加/编辑弹窗加一个「确认天数」输入（`Panel/AlertView.swift:384-386` 阈值输入旁边）。

**验收判据**：
- `confirmDays = 2`，造「第一天收盘跌破、第二天收盘涨回阈值上方」→ 状态回 `idle`，不推送。
- `confirmDays = 2`，造「第一天跌破、第二天仍在阈值下方 0.3%」→ 停在 `counting`，不推送（HOLD 冻结，不是清零）。
- `confirmDays = 2`，造「连续两天收盘在阈值下方」→ `confirmed`，推 1 条。

### W3 判定事件表：历史留痕

**现状**：状态就一个布尔，存在 `UserDefaults` 里。

```swift
// Alert/AlertRule.swift:32-33
var triggered: Bool         // 已触发标记（防重复）
var triggeredAt: Date?      // 触发时间
```

```swift
// Config/AlertConfig.swift:47-55
func updateStatus(at index: Int, triggered: Bool) {
    guard index < rules.count else { return }
    if triggered { rules[index].markTriggered() } else { rules[index].reset() }
}
```

`markTriggered()` 覆盖 `triggeredAt`（`AlertRule.swift:38-41`），所以**同一条线当天只可能留下一次触发时间**，而且没有「哪几天响过、当时什么价」的记录。通知中心也倒推不出来 —— `identifier` 用 `rule.id`，新通知顶掉旧的（`Alert/AlertNotifier.swift:92-96`）。

**对照**：my-app 的判定层是自家的表，与通知的生命周期解耦（`api/db.js:172-188`）：

```sql
CREATE TABLE IF NOT EXISTS market_alert_event (
  id         INTEGER PRIMARY KEY AUTOINCREMENT,
  user_id    INTEGER NOT NULL DEFAULT 1,
  rule_id    TEXT    NOT NULL,               -- 配置里那条线
  secid      TEXT    NOT NULL,               -- 标的（展示名 / 跳转目标）
  code       TEXT    NOT NULL,               -- 判定价代码
  pdate      TEXT    NOT NULL,               -- 判定价自带日期
  price      REAL    NOT NULL,
  state      TEXT    NOT NULL,               -- idle / counting / confirmed
  days       INTEGER NOT NULL DEFAULT 0,     -- 用户看到的「第 N 天」
  first_hit  TEXT,                           -- 本轮计数起点
  notified   INTEGER NOT NULL DEFAULT 0,
  created_at TEXT    NOT NULL DEFAULT (datetime('now'))
);
CREATE UNIQUE INDEX IF NOT EXISTS ux_mae_rule_date ON market_alert_event (user_id, rule_id, pdate);
```

三条设计约束（`api/db.js:843-848`）：

1. 幂等靠**唯一索引** + `INSERT OR IGNORE`，不是代码级「先查再插」（`api/db.js:904-920`）。
2. **「当前状态」= 该线 pdate 最大的那一行**，不另存一份 —— 状态与历史永远一致，不会出现「历史说第 3 天、状态说第 1 天」的两处漂移（`api/db.js:852-864`）。
3. 判定表长期保留（730 天），通知当天过期。两者生命周期必须不同（`api/db.js:166-170`）。

为什么不能用「只活一天」的东西当判据：旧实现靠通知的 dedupe 前缀反推「这条线以前提醒过没有」，而到价通知 `expiresAt` = 当天 23:59:59，次日被清掉，那段判据在线上是死代码（`api/db.js:166-170`）。

**改法**：新建 `Alert/AlertEventStore.swift`。App 里还没有数据库层，两个选项：

- **(a) 系统 SQLite3**（`import SQLite3`，直接走 C 接口）：唯一索引、`INSERT OR IGNORE`、按 pdate 取最大行都能落到 SQL，约 150 行。选它。
- (b) JSONL 追加文件：实现快，但「同日幂等」要自己在内存里查重，且文件会一直涨。不选。

表结构照抄 my-app，字段名可去掉 `user_id`。配套 4 个查询：`latest(ruleId)` / `history(ruleId, limit)` / `record(...)` / `markedNotified(ruleId, pdate)`（对应 `api/db.js:852-930`）。

原有的 `triggered` / `triggeredAt` 保留为**运行态**（界面即时显示用），结论以事件表为准。

**验收判据**：事件表写完的当天，规则列表上能显示「最近触发 09-18」；连造三天穿越，`history` 返回 3 行，日期各不相同。

### W4 判定时点：两道闸门

**现状**：没有时点概念。拿到数据就判 —— 而数据 30 秒一轮，黄金到半夜两点还在动。

**对照**：my-app 两个常量（`api/market-poller.js:101-107`）：

```js
const EVAL_QUOTE_MIN = 15 * 60 + 35;   // 场内 15:35 —— 日盘已收，此刻读数 = 收盘价
const EVAL_FUND_MIN  = 20 * 60 + 30;   // 场外 20:30 —— 净值 19:00 起陆续披露
```

注释写明了这道闸门为什么不能省：

> ⚠️ 这个闸门**不可省**：没有它，黄金会拿夜盘 02:30 的读数当「今日收盘价」判定（pdate 在同一天内不变，但那个价不是收盘价，违反「只取日盘收盘」）。

判定前的顺序（`api/market-poller.js:426-435`）：

1. 取判定价自带日期，拿不到或晚于今天 → 不评估；
2. 当前时刻未到该品种的判定时点 → 等下一轮；
3. 该 pdate 已判过 → 跳过（幂等）。

**改法**：新建 `Alert/JudgeWindow.swift`，两个函数：

```swift
/// 场内（黄金 / 板块）：工作日 15:35 之后
static func quoteJudgable(_ now: Date) -> Bool

/// 场外基金：工作日 20:30 之后
static func fundJudgable(_ now: Date) -> Bool
```

`checkAlerts()` 里按 `rule.targetType` 分流：`.goldCNY` / `.sector` 走前者，`.fund` 走后者。未到窗口的线直接跳过，不计入「无行情」（这一点和 W8 联动 —— 净值窗口里本来就不该拿旧快照评估，`api/market-poller.js:410-412`）。

对基金还要多一步：只认**当日**的 `navDate`。净值窗口内拿到昨天 PDATE 的净值是常态（`api/market-poller.js:102-103`），必须等到 PDATE 变成今天才是当日的权威值。现在 App 拿不到这个判断 —— `FundQuote.navDate` 在（`DataLayer.swift:366`），但没人检查它。

**验收判据**：
- 22:00 拿到黄金 705、当日日盘收盘 698 → 不推送。
- 16:00 拿到板块收盘涨跌幅 -2.3%、阈值 -2.0% → 推送。

### W5 判定要跑得起来：盘后窗口与补扫

**现状**：判定挂在 `refresh()` 末尾，而 `refresh()` 受定时器门禁控制。

```swift
// MenuBarController.swift:325-327
private var anyMarketOpen: Bool {
    goldMarketStatus == .trading || goldMarketStatus == .delayed || stockMarketStatus == .trading
}
```

```swift
// MenuBarController.swift:332-337
let t = Timer(timeInterval: 30, repeats: true) { [weak self] _ in
    guard let self else { return }
    if self.anyMarketOpen { Task { await self.refresh() } }
}
```

工作日 15:00 之后，黄金日盘收（`:295-298`），夜盘 21:00 才开（`:283`），A 股 15:00 收（`:310`）。于是 **15:00–21:00 `anyMarketOpen` 恒为 false**，定时器一次都不跑。

唯一还能触发判定的是打开面板：

```swift
// MenuBarController.swift:207-210
private func showPanel() {
    guard let button = statusItem.button else { return }
    Task { await refresh() }        // 这条路径不受 anyMarketOpen 门禁
```

所以现在的实际行为是：**基金净值告警只在「你主动打开面板」时才会被评估**。19:30 净值出来时如果没打开面板，这条线就不判；等到 21:00 夜盘开盘才开始跑，那时已经在按 W4 的时点闸门评估基金了。

还有一处更彻底的静默：**Mac 睡眠期间 App 完全停摆，醒来不做任何补判**。白天睡一下午，收盘价那一刻正好错过，这条线当天就不响了。

**对照**：

三个运行窗口（`api/market-poller.js:70-79`）：

| 窗口 | 区间 | 用途 |
|---|---|---|
| 交易时段 | 周一~五 09:25–15:05 + 沪金夜盘 21:00–次日 02:30 | 抓即时行情（仅展示用） |
| 收盘取价窗口 | 工作日 15:05–16:30 | 抓当日收盘价，判定时点设在 15:35 |
| 净值窗口 | 工作日 15:05–24:00 | 只抓基金，19:00 起陆续公布 |

补扫机制（`api/scheduler.js:14-16`）：

> **启动补扫**：旧实现是 setTimeout 递归且防重只防不补 —— 重启错过 02:00 就整日跳过扫描（现存静默缺陷）。现在改为「每分钟 tick + 判断今天是否已跑过」，启动后第一个 tick 天然完成补扫，且免疫 setTimeout 漂移与机器休眠。

判断「今天跑过没」读的是**任务的产出**（dedupe_key 是否已在库里），所以重启后的进程也能认出来（`api/scheduler.js:124-144`、`:190-193`）。

**改法**：
1. `anyMarketOpen` 改名扩义，拆成三个谓词：`goldMarketStatus` / `stockMarketStatus` / `fundNavWindow`（工作日 15:05 之后）。
2. 定时器间隔按窗口分档：交易时段 30s，纯净值窗口 5 分钟（净值一天只变一次）。
3. 加**唤醒补判**：`NSWorkspace.didWakeNotification` 与 App 启动时各跑一轮，判据用 W3 事件表 —— 「这条线的今天 pdate 有没有行」比时间戳可靠。
4. 补扫完成后再决定要不要发通知：如果 pdate 是今天的收盘价、且满足确认天数，就推 —— 迟到的通知也比没有通知好，但标题里要说明是哪天的判定价（W6）。

**验收判据**：
- 15:10、19:30 两个时刻，`fundNavWindow` 均为 true；19:30 那轮能拿到当日 PDATE 的净值。
- 把系统时间设到 15:36，睡眠到 16:10 唤醒 → 事件表里出现今天 pdate 的行，通知带今天的日期。
- 周末 19:30，`fundNavWindow` 为 false。

### W6 通知内容：说清楚是第几天、什么价

**现状**：

缺三样东西：**这是哪天的判定价**（盘中价还是收盘价，看不出）、**第几天**（连续第 1 天和第 3 天紧迫程度差很远）、**同时还命中了哪条线**。

**对照**：my-app 的标题必须带天数（`api/market-poller.js:978-981`）：


标题：`"{标的名} · {label} · 第 {days} 天"`（label 过长时截断，说明放正文）。

第二行说明，第三行同时命中。

**验收判据**：造一条 `confirmDays = 2`、第二天命中、同时击穿两条线的场景，通知标题含「第 2 天」，正文含判定价、确认天数、同时命中的另一条线名。

### W7 同品种同日多条线命中合并为一条

**现状**：`checkAlerts` 逐条遍历，命中的逐条发（`MenuBarController.swift:532-538`）。

**对照**：my-app 按 `secid` 分组，同日同品种的多条线合并成一条通知，其余以「同时命中」出现在正文（`api/market-poller.js:964-970`、`:990-992`）：

### W8 拿不到判定价必须留痕

**现状**：数据拉失败时，规则**整条不参与评估**，而界面上什么都不说。

```swift
// MenuBarController.swift:426-430
} catch let error as FetchError {
    self.errorMessage = "\(error.localizedDescription)（已显示上次数据）"
} catch {
    self.errorMessage = "更新失败，请稍后重试"
}
```

错误提示挂在面板顶部（`errorMessage`），但**规则行本身没有任何标记**。板块接口挂了一整天，你在规则列表上看不出那条 -2% 的线已经一天没在工作了。这是 my-app 那边踩过的最恶劣的一环（`api/market-poller.js:66-68`）：

> `pickAlerts` 会把它们收进 `missing`，run 写日志 + 落 `noQuoteAt` —— 旧实现静默 `return`，用户配的线形同不存在且系统一言不发。

**对照**：三个细节值得照抄。

1. **「没拿到」的判据**：`price == null` **或 `price == 0`** 都算没拿到。东财在非推送时段会回 `f2: 0.0`，而解析函数会把 0 当合法价 —— 那会让「跌破 905」这类低线被 0 **假触发**，比不触发更糟（`api/market-poller.js:415-417`）。App 的 `fetch()` 里 `(first["f2"] as? Double) ?? 0` 正好会掉进这个坑（`DataLayer.swift:104`）。
2. **首次标记写时间，持续故障时时间戳稳定** —— 否则每轮都变，界面轮询到变化就重绘，且看不出「从什么时候开始没行情」（`api/market-poller.js:1025-1027`）。
3. **有判定价的一轮要清掉标记**，否则一次网络抖动会永久挂着「未生效」（`:1021`）。

还有一条反向规则：**本轮没抓过这个判定价 → 不评估、也不标「无行情」**。净值窗口里交易所族本来就不抓，拿上一轮快照里的旧价评估会凭空造出一次穿越（`api/market-poller.js:410-412`）。这条与 W4 的时点闸门是同一个道理。

**改法**：
1. `MenuBarController` 加 `@Published var unjudgedRules: [String: Date]`（ruleId → 首次无判定价的时刻）。
2. `checkAlerts` 收集 `missing`，写入上述字典；有价的线清掉自己的条目。
3. 数据解析层：`f2 == 0` 或缺失时抛错，不要回退成 0（`DataLayer.swift:104`、`:108`）。
4. 规则行按 W10 显示「未生效 · 无行情」。

**验收判据**：断网 30 分钟后恢复 → 断网期间规则行显示「未生效 · 无行情」且时间戳不变；恢复后标记消失。造一段 `f2: 0.0` 的响应，那条低线不得触发。

### W9 通知标识与两层幂等

**现状**：

```swift

    identifier: rule.id,
    content: content,
    trigger: UNTimeIntervalNotificationTrigger(timeInterval: 0.1, repeats: false)
```

同一 rule 的新通知会顶掉旧的。这是 `UNNotificationRequest` 的行为，不是 bug，但结果是通知中心留不下多次记录。

**对照**：my-app 有两层不同的幂等，职责分开（`api/market-poller.js:1005-1008`）：

> `dedupeKey` 带**判定价日**（不是自然日）：同品种同一判定价日只可能有一条通知。⚠️ 它与判定表的 `(rule_id, pdate)` 唯一索引是**两层不同的幂等**：那张表管「一天只判一次」，这条键管「一天只推一条」。

```js
expiresAt: sh.date + 'T23:59:59+08:00'
```

通知层的唯一入口在 `api/notify.js:65-91`，落库前校验 `module` / `kind` / `title` 必填，`dedupeKey` 撞了返回 `{created:false}` 且不抛错（幂等是正常路径，不是异常）。

**改法**：
1. `identifier` 改为 `"\(rule.id)-\(pdate)"`。同一线同一判定价日只推一次，不同日期各自留痕。
2. W3 落表之后这条改动才有意义 —— 否则通知中心一堆重复项，没有历史可对。

**验收判据**：连推三天，通知中心能看到三条，标题天数各不相同。

### W10 规则行上的状态呈现

**现状**：规则行第二行只有两种状态。

```swift
// Panel/AlertView.swift:209-221
HStack(spacing: 4) {
    if rule.triggered, let t = rule.triggeredAt {
        AppIcon(name: "check-circle", size: 10).foregroundColor(.orange)
        Text("已触发 \(t, format: .dateTime.hour().minute())")
            .font(.caption2).foregroundColor(.orange)
    } else {
        Text(rule.label).font(.caption2).foregroundColor(.secondary)
    }
}
```

触发 → 「已触发 14:32」；未触发 → 显示规则本身的提醒文案（配置文本，不是状态）。

看不出三件事：**还差几天**、**这条线现在没在跑**、**上次是什么时候响的**。

**对照**：my-app 前端有五种状态，优先级有明确规则（`public/assets/market.js:1290-1303`）：

| kind | 含义 | 样式 | 优先级说明 |
|---|---|---|---|
| `hit` | 今日推送过 | 红 | 唯一「要你动手」的状态 |
| `counting` | 已在触发区、天数未满 | 深灰 medium | 文案带 `第 N/M 天` |
| `confirmed` | 纪律已成立（连续 N 日） | 深灰 medium | 稳态不染色（长期染色 = 噪音） |
| `dead` | 未触发且拿不到判定价 | 琥珀 | 数据运行态 |
| `last` | 非今日的旧触发 | 常态色 | 「最近触发 MM-DD」 |

两条优先级规则值得注意（`:1295-1302`）：`hit` 要排在 `state` 前面（否则用户永远看不到「今日已触发」那一天）；`dead` 要排在 `counting` / `confirmed` **之后** —— 「没拿到行情」是数据运行态，「连续第几天」是长期结论，旧实现让前者盖掉后者，一次网络抖动就把「纪律还在成立」这件事藏了起来。

服务端派生状态、前端只读展示，前端不自己算「第几天」（`public/assets/market.js:1237-1241`）。

**改法**：`AlertRuleRow` 的第二行改成一个 `kind` 驱动的状态描述，取值与优先级照抄上表。数据来源：W3 事件表（state / days / pdate）+ W8 的 `unjudgedRules`。

**验收判据**：造四条线分别处于 `hit` / `counting` / `dead` / `last` 状态，规则列表在同一屏里正确显示四种文案与配色；`dead` 与 `counting` 并存时显示 `counting`。

### R2 行情加第二数据源

**现状**：三类行情各只有一个东财接口，无降级链、无退避。

| 数据 | 接口 | 证据 |
|---|---|---|

**对照**：交易所族四级（`api/market-poller.js:13-14`、`:490-548`）：

```
ulist 批量 → qt/stock/get（node fetch）→ qt/stock/get（/usr/bin/curl）→ 新浪 hq.sinajs.cn
```

第三级的理由写得很直接：`node 指纹被掐 → curl 兜底`（`:515`）。基金族两级**真异源**：天天基金首发 → 未覆盖的交给新浪 `hq.sinajs.cn/list=f_xxxxxx`（GBK）。选新浪而不选东财自家的 `f10/lsjz`，是因为同厂商「一家收紧就一起收紧」（`:16-28`、`:687-692`）。

**改法**：定义 `protocol QuoteSource { func fetch(...) async throws -> ... }`，`GoldService` / `SectorService` / `FundService` 各持一条有序链，成功即返回，全败才抛错。命中源记进数据模型（`source: String`），错误提示能说出「三个源都失败」。

**实际做法**：没有用 protocol（三类行情的返回类型各不相同，protocol 会变成三个协议），改成一个泛型执行器 `QuoteChain.run([QuoteSource<T>])`。命中源记进数据模型；全败抛 `FetchError.allSourcesFailed([String])`，错误文案形如「全部数据源失败（东财延时 / 东财主站 / 东财单只）」。

**一处偏离**：场内品种**没有**接新浪。实测新浪 `list=nf_AU0` 与东财 113.aum 不是同一合约口径（935.78 vs 933.02），绝对价格阈值跨源切换会凭空触发。黄金与板块改为「东财两个网关 + 两种接口形态」三级。基金是唯一跨厂商的一级，因为两源实测逐值吻合。详见 §4b 的降级链表。

**验收判据**：把首选源域名指向不可达地址，App 仍能显示行情，错误提示里出现「已切换数据源」。

场内品种用新浪 `hq.sinajs.cn`（要带 `Referer: https://finance.sina.com.cn`，不带直接回 `Forbidden`，`api/market-poller.js:118-120`）。

### R3 数据时效可见

**现状**：主卡片没有行情时间。

顶部标题栏显示的是「N 秒后更新 / 刷新中 / 已收盘」（`Panel/MainPanelView.swift:78-95`）—— 那是**刷新倒计时**，不是**数据时间**。

这里还有一个被 W1 暴露出来的问题：`GoldQuote.time` / `.date` 是本地时钟格式化的（`DataLayer.swift:109-110`），**它显示的是抓取时刻，不是行情时刻**。周末显示的会是「刚刚」，而盘面是周五的。

**对照**：my-app 把行情时间当成必须显式携带的字段，并明确禁止用抓取时间冒充：

> `f124` = 行情自身更新时间（unix 秒）：总览卡「截至 MM-DD HH:mm」的数据来源 —— 东财只在交易时段推送，周末快照是周五的，绝不能用 `fetchedAt` 冒充行情时间
> —— `api/market-poller.js:150-152`

前端三处统一（`public/assets/market.js:387`、`:742`、`:837`），延迟附加在同一串上：`最后更新 MM-DD HH:mm · 数据延迟 N 分钟`。阈值 `STALE_MS = 10 * 60 * 1000`，超过转红（`market.css:29-31`）。**只在交易时段内判定陈旧** —— 周末看到上周五的盘面是常态（`market.js:379-380`）。

**改法**：
1. 依赖 W1 第一步的 f124（同一处改动，不重复做）。
2. `PriceHeader` 加 `updatedAt: Date?`，渲染在 `secondary` 同行右侧。
3. 加 `DataFreshness` 工具，`stale(after: 600)` 返回 Bool 与延迟文案，三处共用。
4. `MarketStatus.delayed` 从「只有黄金」推广到三个 Tab（现在 `stockMarketStatus` 永远只返回 `.trading` / `.closed`，`MenuBarController.swift:302-312`），阈值统一 10 分钟，只在交易时段内判定。

**验收判据**：断网 12 分钟后三个 Tab 时间戳转红并显示「数据延迟 12 分钟」；周末打开时不转红。

**实际做法**：`PriceHeader` 的参数叫 `quoteAt: Date?`（不叫 `updatedAt` —— 名字要能区分「行情时间」与「抓取时刻」）。陈旧用**琥珀色 `#F59E0B`** 而不是红色：同一屏里 `delayed` 徽标就是这个色，两处表示同一件事却用两种颜色会让人以为是两回事。判定阈值 600s，只在 `.trading` / `.delayed` 下判。

### R5 基金估值标覆盖度

**现状**：

```swift
// Data/FundEstimator.swift:12-25
static func estimateChangePct(holdings: [FundHolding], stockMap: [String: Double]) -> Double? {
    var weightSum = 0.0
    var weighted = 0.0
    for h in holdings {
        let key = normalizeCode(h.code)
        if let pct = stockMap[key] {      // 拿不到行情的重仓，直接跳过
            weightSum += h.weight
            weighted += h.weight * pct
        }
    }
    guard weightSum > 0 else { return nil }
    return weighted / weightSum           // 分母是「有行情那部分」的权重和
}
```

10 只重仓只有 2 只有行情时，函数照样返回一个数，界面上看不出它只代表 2 只股票的加权。

**改法**：返回 `(pct: Double, coverage: Double)`，`FundView` 在估算值旁标注「按前 10 大重仓 · 覆盖 62%」，低于 50% 时数值置灰。
